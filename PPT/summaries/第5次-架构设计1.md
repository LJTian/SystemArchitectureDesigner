## 三、核心考点与原理详解

### 1. 五大通用架构风格与子风格全景

| 架构大类 | 子风格 | 构件类型 | 连接件类型 | 核心特点与典型应用 |
| :--- | :--- | :--- | :--- | :--- |
| **数据流** | **批处理序列** | 独立应用程序 | 某种媒介 | 构件间必须等待前一步全部处理完毕，**整体批量传递** |
| | **管道-过滤器** | 过滤器（Filter） | 管道（Pipe） | 每个构件流式输入输出，**无状态、支持并行**（如 Unix 管道、传统编译器） |
| **调用/返回** | **主程序/子程序** | 过程/模块 | 过程调用 | 单线程控制，调用关系分层，主程序正确性依赖子程序 |
| | **面向对象** | 对象（抽象数据类型） | 方法调用 | 封装性、数据隐蔽，通过对象交互协作 |
| | **分层架构** | 层内构件 | 层间协议接口 | **每层仅使用下层服务并为上层服务**，降低复杂度但有通信开销 |
| | **C/S 与 B/S** | 客户端/服务端/浏览器 | 网络协议 | 两层（胖客户端）、三层（瘦客户端+应用服务+DB）、B/S（零客户端） |
| **数据为中心** | **仓库（Repository）** | 中央数据结构 + 独立构件 | 数据存取协议 | 构件主动访问被动数据库，状态集中管理（如 IDE 工作区） |
| | **黑板（Blackboard）** | **知识源 + 黑板 + 控制部件** | 状态触发通知 | **适用于非结构化、求解流程不确定的复杂问题**（语音/模式识别/专家系统） |
| **虚拟机** | **解释器** | **解释引擎 + 存储区 + 状态表** | 数据访问与控制 | 弥合程序与硬件语义差异，灵活性极高但执行速度慢（如 Python/JVM 字节码引擎、脚本系统） |
| | **规则系统** | 规则集 + 规则解释器 + 工作内存 | 规则匹配 | 人工智能与决策支持系统（DSS），基于专家经验规则推理 |
| **独立构件** | **进程通信** | 命名进程 | 消息传递 / IPC | 点对点或异步同步消息传递，构件独立运行 |
| | **事件系统（隐式调用）** | 事件源 + 事件处理器 | **事件注册与派发** | **构件松耦合**，触发事件时不需知道谁在监听（发布-订阅模式） |

### 2. 软件质量属性体系与场景六要素

- **质量属性分类辨析**：
  - **开发期质量属性**：易理解性、可扩展性、可重用性、可测试性、**可维护性**、可移植性。
  - **运行期质量属性**：**性能**（响应时间/吞吐量）、**可用性**（故障率/MTBF/恢复时间）、**安全性**（机密性/完整性/不可抵赖）、**可伸缩性**、**互操作性**、**鲁棒性/健壮性**、**易用性**。
- **质量属性场景（Quality Attribute Scenario）六要素（必考）**：
  1. **刺激源（Source of stimulus）**：生成刺激的实体（如用户、攻击者、定时器、内部故障）。
  2. **刺激（Stimulus）**：到达系统并需响应的事件（如突发高并发请求、网络断开、系统更新）。
  3. **环境（Environment）**：刺激发生时的系统状态（如正常运行、超载峰值、断网恢复期）。
  4. **制品（Artifact）**：受刺激影响的系统局部或组件（如支付网关、核心数据库、缓存层）。
  5. **响应（Response）**：刺激到达后系统执行的具体动作（如熔断降级、切换主备、记录日志）。
  6. **响应度量（Response Measure）**：对响应结果的**量化测试指标**（如“响应时间 $< 200\text{ ms}$”、“故障恢复时间 $< 30\text{ s}$”）。

### 3. 系统架构评估核心概念与方法

- **四大核心概念（案例分析第 1 题必背）**：
  - **敏感点（Sensitivity Point）**：为了实现某种特定质量属性，对系统构件特性或关系的取值要求（如“响应时间敏感于数据库连接池大小”）。
  - **权衡点（Trade-off Point）**：**同时影响多个质量属性，且往往在此消彼长的敏感点**（如“采用高强度数据加密提升了安全性，但降低了系统响应性能”）。
  - **风险点（Risk）**：架构设计中可能导致严重负面后果的潜在隐患（如“单点 Redis 宕机将导致整体下单不可用”）。
  - **非风险点（Non-risk）**：经过设计验证能够良好满足要求、不会带来负面后果的安全决策。
- **三大主流评估方法演进**：
  - **SAAM（软件架构分析方法）**：最早由 Rick Kazman 提出，**最初主要针对可修改性**，后扩展为通用架构评估。
  - **ATAM（架构权衡分析方法）**：主要关注**性能、可用性、安全性、可修改性**等属性之间的权衡；核心工具为**效用树（Utility Tree）**；分为四个阶段（演示、调查与分析、测试、报告）。
  - **CBAM（基于成本效益的架构分析方法）**：在 ATAM 基础上引入经济学考量，**评估架构变更的成本、收益与投资回报率（ROI）**。

---

### 4. 效用树（Utility Tree）结构与优先级评定

- **效用树四级结构**：
  $$\text{根节点（Utility）} \to \text{质量属性（如性能）} \to \text{属性分类（如响应时间/吞吐量）} \to \text{叶子节点（具体场景描述）}$$
- **优先级评定机制**：
  - 每个叶子节点场景被赋予两个维度的优先级：
    $$\text{(对系统成功的重要性，实现的难易程度/风险)}$$
  - 取值范围为 `(H/M/L, H/M/L)`，其中 `(H, H)` 为首要重点关注的场景。

## 四、经典案例分析与答题实战

### 【案例 1】电动车充电管理系统质量属性辨析（2025.11 真题）

#### 需求描述与属性对应
1. “充电桩网络连接中断时，充电桩应能离线记录充电数据，待网络恢复后自动上传并完成结算。” $\implies$ **可用性 / 鲁棒性**
2. “对充电订单和用户敏感数据采用国密 SM4 算法加密存储，防止非授权窃取。” $\implies$ **安全性**
3. “在 10 万辆车同时在线充电并发请求时，系统平均响应延迟不超过 0.5 秒。” $\implies$ **性能**
4. “未来系统接入新型储能电站时，无需修改核心调度代码，仅需编写新的设备协议适配器。” $\implies$ **可修改性 / 可扩展性**

#### 权衡点分析与答题规范
- **问题**：说明题干中是否存在架构权衡点，并说明理由。
- **标准答案**：
  存在权衡点。例如在充电桩通信与存储中“采用国密 SM4 算法加密数据”即为一个典型的权衡点。该设计**提升了系统的安全性（阻止数据泄露），但加密/解密运算消耗了计算资源并增加了通信延迟，从而降低了系统的响应性能**。

---

### 【案例 2】解释器风格架构核心组件填空（2025.05 真题）

- **解释器四大核心组成部分**：
  1. **解释引擎（Interpretation Engine）**：负责遍历、语法分析并执行指令。
  2. **被解释代码存储区（Source/Bytecode Storage）**：保存待解释的脚本代码或中间表示。
  3. **解释引擎工作状态（State Table / Memory）**：记录变量、符号表及执行上下文。
  4. **解释进度数据结构（Program Counter / Progress）**：记录当前正在解释执行的代码位置。
- **适用理由**：
  用户定义的规则/脚本多变，解释器风格提供了极高的自定义与动态扩展能力，无需重新编译主程序即可热加载执行新逻辑。

## 五、备考与冲刺提示

1. **案例题第一题（25 分）保分秘籍**：
   - 质量属性场景匹配：先划关键词——“并发/秒/吞吐” $\to$ 性能；“宕机/容错/切换/可用率” $\to$ 可用性；“加密/权限/攻击/防篡改” $\to$ 安全性；“新增功能/适配/重构” $\to$ 可修改性。
   - 敏感点与权衡点必须结合题干具体组件叙述，写出“对属性 A 有利，但对属性 B 产生负面影响”。
2. **黑板系统 vs 仓库系统**：
   - 仓库是被动数据源（构件拉取）；黑板是主动触发（状态更新通知知识源）。
